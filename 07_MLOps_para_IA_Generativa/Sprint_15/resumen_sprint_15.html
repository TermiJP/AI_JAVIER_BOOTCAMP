Autenticación y secrets clave del sprint

Sin protección, cualquiera puede llamar a POST /ask y gastar tus tokens. Autenticar = demostrar quién llama; autorizar = qué puede hacer ese quién. Aquí autenticamos la llamada a la API con una API key y decidimos dónde viven las claves.

Sin protección:  cualquiera llama a POST /ask  →  gasto de tokens + datos
Con protección:  solo quien tiene la clave  →  controlamos el uso

Dos claves, dos roles

VariableQuién la usaPara qué
GEMINI_API_KEYNuestra app → GeminiLlamar al LLM
API_KEYCliente → nuestra APIDemostrar que puede usar /items o /ask

La clave de Gemini nunca se manda al navegador ni se pone en Swagger. La API_KEY sí la envía el cliente (Swagger, Postman, Streamlit…).

Qué pasa si falta cada unaSin GEMINI_API_KEY el servidor no arranca (RuntimeError en gemini_auth.py). Sin API_KEY sí arranca, pero cada petición protegida responde 503.

Reglas rápidas de secrets

  • Secretos solo en entorno (.env local; panel del PaaS en S16).
  • Subimos .env.example sin valores reales.
  • .env en .gitignore.
  • Si falta API_KEY en el servidor → mejor fallar claro (503 en cada petición protegida) que dejar la API abierta «por defecto».
# .env.example (resumido; el de la Live Review tiene estas variables)
GEMINI_API_KEY=
API_KEY=cambia-esta-clave
RATE_LIMIT_PER_MINUTE=30
CORS_ORIGINS=http://127.0.0.1:8000,http://localhost:8000,http://127.0.0.1:8501,http://localhost:3000
ASK_TIMEOUT_SECONDS=300
Cambia la clave de ejemploSi dejas API_KEY=cambia-esta-clave, el servidor arranca y esa clave vale: cualquiera que lea el repo la conoce. Pon un valor propio en tu .env.

API key: el «pase» de la API

Una API key es una cadena aleatoria que nosotros definimos y guardamos en el servidor. El cliente la manda en cada petición; si coincide, pasa. No es un login de usuario humano: es un pase para servicios y herramientas.

Cliente  →  request + api_key  →  nuestra API
                ↓
         ¿Coincide con API_KEY del .env?
           sí → 200 / lógica normal
           no → 401
SituaciónCódigo
Clave correctaSigue el endpoint
Ausente o incorrecta401
API_KEY no configurada en el servidor503

En este sprint la enviamos por query param (GET /items?api_key=…). La misma idea por header (Authorization: Bearer … o X-API-Key) es lo habitual en producción, porque la clave no queda en URLs ni en logs de proxy. En clase basta una clave; en un producto real, una por cliente para rotar o revocar sin tumbar a todos.

Mapa de estrategias

EstrategiaIdea en una frase¿Hands-on?
API keySecreto compartido en cada requestSí
JWTToken firmado (header.payload.signature) tras un login; se verifica firma y expSolo idea
OAuth 2«Entra con Google / empresa»: acceso delegadoSolo idea
Sesión / cookieLogin clásico en webSolo idea

Regla: API key para el contrato servidor↔servidor o una demo; JWT u OAuth cuando haya producto con usuarios y UI de login.

Protección de endpoints con Depends

Ruta¿Clave?Motivo
GET /docs, /openapi.jsonNoDocumentación / aprendizaje
GET /healthNoPulso del servicio (monitores, PaaS…)
/items (CRUD)SíNegocio

from fastapi import Depends, Query, HTTPException

def require_api_key(api_key: str | None = Query(default=None)):
    if not config.API_KEY:
        raise HTTPException(status_code=503, detail="API_KEY no configurada")
    if not api_key or api_key != config.API_KEY:
        raise HTTPException(status_code=401, detail="API key inválida o ausente")
    return api_key

@app.get("/items", dependencies=[Depends(require_api_key)])
def list_items(...):
    ...

En /docs (Swagger), las rutas protegidas muestran el campo api_key: Try it out → pega el valor del .env → Execute.

✅ Límites asumidos: la API key no sustituye HTTPS (llega con el PaaS en S16), no da identidad ni roles, y si se filtra hay que cambiarla. Va de la mano del rate limit.
❌ Nunca devolvemos la clave en el JSON, ni un stack trace, ni escribimos api_key=… con el secreto en nuestros logs. Ojo: como la clave va en la query, el access log de uvicorn sí imprime la URL completa (POST /ask?api_key=…). Para evitarlo: --no-access-log, enviarla por header, o usar una clave de práctica que luego se cambia.

Errores típicos

  • Poner la API_KEY en el código o en el repo Se filtra en Git. Va en .env (ignorado) y se sube solo .env.example sin valores.
  • Confundir API_KEY con GEMINI_API_KEY La primera protege nuestra API; la segunda llama a Gemini. Una nunca se manda al navegador.
  • Dejar la API abierta si falta la clave Debe responder 503 (servidor mal configurado), no dejar pasar a todos.
  • Mezclar 401 con 503 401 es fallo del cliente (sin clave o mala); 503 es fallo de configuración del servidor.
  • Proteger también /health y /docs Los monitores y el aprendizaje necesitan esas rutas abiertas.

Rate limit, timeouts y errores

Aunque tengamos API key, hace falta limitar cuántas peticiones entran y cuánto puede durar un trabajo. Un bucle mal escrito puede disparar el coste del LLM o la CPU. Python decide esos topes; el cliente recibe códigos HTTP claros.

Rate limiting

Contamos peticiones por API key en una ventana de tiempo (p. ej. 1 minuto). Si se supera → 429 Too Many Requests. En memoria (dict / deque) vale para demo; en producción, Redis u otro almacén compartido.

misma API_KEY · 30 req/min     →  OK
misma API_KEY · 31ª en ese min →  429 Too Many Requests
import time
from collections import defaultdict, deque
from fastapi import HTTPException

_hits: dict[str, deque[float]] = defaultdict(deque)

def check_rate_limit(api_key: str) -> None:
    now = time.monotonic()
    window = 60.0
    q = _hits[api_key]

    while q and (now - q[0]) > window:
        q.popleft()                      # limpiamos hits viejos

    if len(q) >= config.RATE_LIMIT_PER_MINUTE:
        raise HTTPException(status_code=429,
                            detail="Demasiadas peticiones; esperad un minuto")

    q.append(now)                        # registramos este hit
✅ Se llama después de validar la API key. El límite vive en .env (RATE_LIMIT_PER_MINUTE).
❌ No sustituye la API key, no es un WAF, y el contador en RAM se reinicia al reiniciar uvicorn.

En W1 (CRUD seguro): el .env.example baja a propósito RATE_LIMIT_PER_MINUTE=10 para forzar el 429 fácilmente (el de la Live Review usa 30). Además, GET /items pagina con skip, limit y el filtro on_offer.

Timeouts

Una llamada externa (LLM, HTTP, tool) no puede colgar el proceso para siempre. Ponemos un tope en config y, si se pasa, devolvemos 504; el detalle va solo a los logs.

PiezaEjemplo
ConfigASK_TIMEOUT_SECONDS=300 (margen) o 15 para forzar el 504
Si se pasa504 con mensaje claro al cliente
DetalleSolo en logs (con thread_id y limit_s)
 
from concurrent.futures import ThreadPoolExecutor
from concurrent.futures import TimeoutError as FuturesTimeoutError

def _con_timeout(fn, *args):
    # Sin `with`: el 504 sale al llegar al límite (el hilo sigue en segundo plano)
    pool = ThreadPoolExecutor(max_workers=1)
    future = pool.submit(fn, *args)
    try:
        return future.result(timeout=config.ASK_TIMEOUT_SECONDS)
    finally:
        pool.shutdown(wait=False)

try:
    out = _con_timeout(_turno)
except FuturesTimeoutError:
    raise HTTPException(status_code=504,
                        detail="El turno del agente superó el tiempo máximo") from None
OjoA los N segundos la API decide el 504, pero el cliente puede recibirlo un poco después si el LLM/SDK sigue en el hilo de fondo. Lo que cuenta: status 504 + log del límite.
⚠️ El 504 no mata el hilo. El turno sigue ejecutándose en segundo plano: sigue gastando cuota de Gemini y, si llega otro /ask con el mismo thread_id mientras tanto, ambos pueden pisar el mismo estado de sesión. Tras un 504, espera a que termine o usa otro thread_id.

En la versión del alumno el timeout envuelve solo POST /ask; /approve no lo tiene aunque el .env.example hable de «/ask y /approve».

CORS: qué es y qué no es

CORS es una regla que aplica el navegador: una página servida desde un origen (p. ej. localhost:3000) solo puede llamar a otro origen si la API responde diciendo que lo permite. Se configura con CORSMiddleware y CORS_ORIGINS.

  • No protege la API. curl, Postman o cualquier script ignoran CORS; lo que protege es la API key.
  • No interviene con Streamlit: llama con requests desde Python, no desde el navegador.
  • No interviene con Swagger (/docs): se sirve desde el mismo origen que la API.
  • allow_origins=["*"] no es compatible con allow_credentials=True: con credenciales hay que listar los orígenes explícitos, como hace CORS_ORIGINS.

Errores al cliente

CódigoCuándo
401API key ausente o incorrecta
429Rate limit superado
422Body inválido (Pydantic)
400Regla de negocio: p. ej. pregunta vacía en /ask o «no hay plan pendiente» en /approve
404No existe el recurso: p. ej. /approve sin sesión para ese thread_id, o un ítem del CRUD
409Conflicto de negocio (CRUD de W1, p. ej. ítem duplicado)
503Falta configuración (API_KEY no definida)
504Timeout de trabajo
500Error inesperado; mensaje genérico al cliente (los fallos del agente salen como 200 con error, ver §5)

Además del timeout: tamaño y forma del body → Pydantic (422), y topes del agente (max_turns…) en código, no «confiando en el prompt». Misma filosofía que en S14: límites en Python.

Errores típicos

  • Rate limit antes de validar la clave Cualquiera podría llenar el contador de una clave ajena. Primero 401/503, luego check_rate_limit.
  • Olvidar reiniciar uvicorn tras cambiar el .env El .env no se recarga solo: el 429/504 «no sale» porque sigue el valor viejo. (--reload vigila los .py, no el .env.)
  • Timeout demasiado bajo Casi todos los /ask acaban en 504. Mide duration_ms de un turno OK y deja margen (≈ 2×).
  • Devolver el traceback al cliente Filtra información interna. Al cliente un mensaje genérico; el detalle, al log.
  • Confiar en que el contador en RAM sirve en producción Se reinicia y no se comparte entre procesos: ahí iría Redis.

Seguridad de tools del agente

Esto no es el ?api_key= de la API HTTP. Es lo que el agente puede hacer por dentro cuando elige una tool. La auth protege quién llama; la seguridad de tools limita qué hace el grafo.

CapaProtegeDónde vive
Auth HTTPQuién llama a la APIsecurity.py, rate_limit.py, Depends
Tools del agenteQué hace el grafo por dentrosrc/tools/, estado, HITL

Riesgos típicos

Fugas y bloqueos

  • Tool que llama a APIs externas sin timeout.
  • Prompt o tool que acaba filtrando GEMINI_API_KEY o datos sensibles en la respuesta.

Acciones irreversibles

  • Borrar, pagar… sin HITL.
  • Tools de más: superficie de ataque que no necesitamos.

Prácticas mínimas

⏱️ Timeout en cada tool

Toda llamada HTTP o tool externa con tope. En la práctica, API_consultar_calidad_aire usa HTTP_TIMEOUT_SECONDS=12.

🙈 Secretos fuera del estado

Nada de claves en el estado que el LLM «ve».

📋 Allowlist

Solo las tools necesarias. En la práctica, la lista real es TOOL_BY_NAME en src/tools/__init__.py: lo que no esté ahí, el agente no puede ejecutarlo.

🙋 HITL

/approve cuando el plan sea sensible (ya visto en S14).

Idea claveNo montamos un producto de «agent security» enterprise. Con estas cuatro reglas el agente ya no va a ciegas.

Errores típicos

  • Tool sin timeout Una API externa lenta cuelga el turno entero hasta el timeout global.
  • Meter la clave en el prompt o en el estado El modelo puede repetirla en su respuesta.
  • Registrar tools «por si acaso» Cada tool extra es algo más que el modelo puede pedir.
  • Acción irreversible sin aprobación humana Borrar o pagar debe pasar por HITL, no por el criterio del modelo.

Logs en local y correlación

Sin señales, depurar un agente es adivinar: cliente → 500… ¿fue la key? ¿el LLM? ¿una tool? ¿timeout? En local basta con logging bien hecho: qué pasó, a qué conversación pertenece y cuánto tardó. Sin Prometheus ni LangSmith: instrumentación en código + lectura humana de logs.

Logging, no solo print

import logging

logger = logging.getLogger(__name__)
logging.basicConfig(level=logging.INFO,
                    format="%(asctime)s %(levelname)s %(message)s")

logger.info("GET /items status=%s duration_ms=%s", status, duration_ms)
logger.error("fallo en /ask: %s", exc)
✅ Sí logueamos: método, path, status y duration_ms; el thread_id cuando hay conversación; tipo de error o mensaje genérico (el detalle al log, no al cliente).
❌ No logueamos: secretos (API_KEY, GEMINI_API_KEY, contraseñas, connection strings) ni bodies enteros con datos personales si no hacen falta. Ojo: tu logger no escribe la clave, pero el access log de uvicorn sí imprime la URL con ?api_key=… (ver §1).
NivelCuándo
INFORequest normal
WARNING401 / 429 repetidos
ERRORFallos 5xx, timeouts

Correlación con thread_id

Sin un id de correlación, las líneas de tres usuarios se mezclan. El thread_id de la conversación sirve también para seguir el rastro: la teoría propone loguearlo en /ask y /approve; en la práctica el TODO 4 lo hace en /ask. Un request_id (UUID por petición, vía middleware) es opcional.

2026-… INFO POST /ask thread_id=demo-1 duration_ms=4200 pendiente_hitl=False
2026-… INFO tool RAG_buscar_en_guia ok thread_id=demo-1   ← ejemplo de nivel tool (no implementado)

La primera línea es el log real de la práctica: lleva thread_id, duration_ms y pendiente_hitl, sin status. La de tool es solo el siguiente nivel posible.

Latencia y errores con el mismo log

SeñalCómo
Latenciaduration_ms al final de la request
ErroresContar 401 / 429 / 5xx a ojo en consola
Coste de tokensLog opcional si el LLM devuelve usage
 
import time

t0 = time.perf_counter()
# ... manejar request ...
duration_ms = int((time.perf_counter() - t0) * 1000)
logger.info("POST /ask thread_id=%s duration_ms=%s", thread_id, duration_ms)

En GenAI, latencias de segundos son normales (un /ask del agente con varias llamadas a Gemini puede tardar 1–3 min). Lo raro no es la duración, sino un /ask sin timeout que podría colgarse indefinidamente.

Errores típicos

  • Usar solo print Sin niveles ni formato estable; no sirve cuando los logs pasen al panel del PaaS.
  • Loguear la api_key o la query completa El secreto acaba en consola y en logs de proxy.
  • No loguear el thread_id Con varias conversaciones a la vez no sabes qué línea es de quién.
  • Medir la duración antes de acabar el trabajo t0 al empezar y duration_ms al final, tras el turno.
  • Volcar el body entero Datos personales en logs sin necesidad.

Agente, calidad y de local a cloud

El log HTTP del borde dice «200». Dentro de un turno de agente (tools + LLM) hace falta un poco más de rastro, una lista corta de comprobación antes de decir «listo» y entender que la misma instrumentación viajará a S16.

Rastro del turno

EventoEjemplo de log
Inicio de turnoask start thread_id=… no implementado
Tooltool=RAG_buscar_en_guia ok duration_ms=… o fail no implementado
Fin de turnoEn el código real: POST /ask thread_id=… duration_ms=… pendiente_hitl=…

Los eventos «no implementado» son una propuesta de la teoría; el código de la práctica solo emite el log del borde. RAG_buscar_en_guia es el nombre real de la tool.

  • HTTP log = capa borde. Tool log = capa agente. Ambas comparten thread_id.
  • En la práctica lo mínimo es el log del borde (POST /ask thread_id=… duration_ms=…); el rastro por tool es el siguiente nivel.

Checklist de calidad (smoke)

PruebaEsperado
GET /health200
/ask con key válidarespuesta no vacía y error vacío (o pendiente_hitl coherente)
/ask sin key401 (y sale en el log)
Rate limit forzado429
⚠️ Un 200 puede esconder un fallo. Si el agente falla (p. ej. Gemini devuelve un error), la API responde 200 con el campo error relleno, no 500. Un smoke test que solo mire «respuesta no vacía» o el status puede dar OK aunque Gemini esté caído: mira siempre error.

No es un lab de evals ni un dataset: es probar a mano los caminos críticos. Si la respuesta del LLM es «rara», se anota; no construimos un juez automático.

De local a cloud

S16  mismo logger.info(...)  →  logs del Web Service en el panel del PaaS

Por eso S15 endurece antes de abrir la puerta: sin clave ni rate limit, una URL pública «se gasta sola» (tokens, CPU). En un producto real hay desarrollo, staging y producción: mismo código de logging, distinta config (nivel, API_KEY, ASK_TIMEOUT_SECONDS, RATE_LIMIT_PER_MINUTE).

Idea claveAl depurar en la nube, el primer sitio sigue siendo el log: ¿401/429? ¿504? ¿falta un secreto en el panel? Misma lectura que en local; solo cambia la pantalla.

Errores típicos

  • Fiarse de que «200» = respuesta buena El borde dice que la request acabó, no que el agente respondiera bien: los fallos del agente salen como 200 con error. Mira respuesta, error y el rastro.
  • Reescribir el logging al subir a cloud No hace falta: el mismo logger.info sale en el panel del PaaS.
  • Hardcodear secretos para el despliegue Viajan en el .env / panel del PaaS, nunca en el código.
  • Montar Prometheus o tracing distribuido ya Queda fuera de alcance: primero logs con evidencia.

                        detail="El turno del agente superó el tiempo máximo") from None

Ojo con los tiemposCada /ask llama a Gemini y a tools: puede tardar ~1–3 min. /health y GET …/messages son rápidos. Tras forzar 429 o 504, devuelve RATE_LIMIT_PER_MINUTE a ~30 y ASK_TIMEOUT_SECONDS a ~300 y reinicia.
Modelo y cuota de GeminiGEMINI_MODEL = "gemini-2.5-flash" (en config.py) puede dar 404 con cuentas nuevas: cambia a un modelo disponible en tu cuenta. Además, la práctica pide al menos 3 /ask y cada uno hace unas 13 llamadas a Gemini, más de lo que da el plan gratuito. Gasta cuota solo donde haga falta: 401, 429 y el historial no llaman al LLM. Un /ask que da 504 sigue gastando cuota en segundo plano.

Checklist del sprint

Conceptos que debes dominar

  • API_KEY ≠ GEMINI_API_KEY; secretos solo en entorno, .env.example sin valores
  • API key por query + Depends; JWT / OAuth, solo la idea
  • /health y /docs abiertos; el resto cerrado
  • Códigos: 401, 429, 422, 503, 504, 500 (y cuándo sale cada uno)
  • Rate limit por clave, ventana de 60 s; límites de ejecución en Python
  • Timeout de turno y de tools; detalle solo en logs
  • Seguridad de tools: timeout, secretos fuera del estado, allowlist, HITL
  • Logs con thread_id y duration_ms, sin secretos; de local a cloud cambia la «pantalla», no el código

Práctica con la Live Review

  • require_api_key: 503 sin config, 401 con clave mala, luego rate limit
  • check_rate_limit devuelve 429 al superar el cupo
  • CORSMiddleware con config.CORS_ORIGINS
  • Log POST /ask thread_id=… duration_ms=… sin secretos
  • Timeout → 504 con log limit_s
  • /health 200 sin clave; /ask 401 sin clave y 200 con clave
  • Forzado 429 y 504, y valores devueltos a 30 / 300
  • python verificar.py --check OK (opcional: Streamlit ask / 401 / historial)

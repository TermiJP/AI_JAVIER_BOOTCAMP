Docker y containerización clave del sprint

Hasta ahora la API corre en nuestro entorno. En la nube (y en el equipo de un compañero) eso se rompe: otra versión de Python, paquetes que faltan, rutas distintas. Docker fija todo eso en una imagen reproducible.

Código FastAPI
    + requirements.txt
    + Python / sistema base
        → imagen Docker
            → contenedor (local o PaaS)

Docker empaqueta código + runtime + dependencias en una imagen. Al ejecutarla nace un contenedor: un proceso aislado con todo lo que necesita.

Sin DockerCon Docker
«En mi PC sí»Misma imagen en local y en cloud
Instalar dependencias a mano en el servidordocker build + docker run
Dudas de versión de PythonLa imagen fija la base

Imagen vs contenedor

ConceptoAnalogíaQué es
ImagenReceta / plantillaCapas de archivos + metadatos (qué comando arranca)
ContenedorPlato servidoProceso en marcha creado desde una imagen
 
docker build -t mi-api:local .
# → crea/actualiza la imagen mi-api:local

docker run --rm --name mi-api -p 8000:8000 --env-file .env mi-api:local
# → arranca un contenedor; con --rm se borra el contenedor al salir, no la imagen

De una misma imagen se pueden lanzar varios contenedores. Frente a una máquina virtual, el contenedor comparte el kernel del host: arranca en segundos y empaqueta una app, no un sistema completo.

Dockerfile mínimo para FastAPI

# Imagen base oficial de Python (ligera)
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install -r requirements.txt

COPY . .

EXPOSE 8000
CMD uvicorn app:app --host 0.0.0.0 --port ${PORT:-8000}
InstrucciónPor qué
FROM python:3.12-slimBase oficial, Python fijo, imagen ligera
WORKDIR /appDirectorio de trabajo dentro del contenedor
COPY requirements.txt + RUN pip …Antes de copiar el código: Docker reutiliza la capa de dependencias si no cambian → builds más rápidos
COPY . .El código de la API
EXPOSE 8000Documenta el puerto (hace falta -p al hacer run)
CMD … --host 0.0.0.0 --port ${PORT:-8000}Escucha en todas las interfaces; 8000 por defecto o el valor de PORT

app:app es archivo:variable, igual que con uvicorn en local. Usamos la forma shell del CMD porque la forma JSON (["uvicorn", …]) no expande ${PORT}, y el hosting puede inyectar PORT.

.dockerignore y secrets

.git
.env
__pycache__
*.pyc
.venv
venv
*.db
.pytest_cache
✅ Código en git · secretos fuera. Los secretos entran en runtime: -e API_KEY=…, --env-file .env o el panel del PaaS. La imagen no lleva claves.
❌ Nunca copiar un .env con claves reales a la imagen. Sin .dockerignore, COPY . . se lo lleva.

Comandos que usaremos

docker build -t nombre:tag .
docker images              # listar imágenes
docker ps                  # contenedores en marcha
docker ps -a               # también los parados
docker logs <nombre-o-id>  # salida de la app
docker stop <nombre-o-id>
docker start <nombre-o-id>
docker rm <nombre-o-id>
docker rm -f <nombre-o-id> # para y borra (útil antes de rebuild)

Vale el nombre o el ID (basta un prefijo si es único). Docker Desktop hace lo mismo con botones (Containers / Images → Stop, Start, Delete).

Puertos: -p host:contenedor

Dentro del contenedor la API escucha en 8000. Con -p 8000:8000 la publicamos en el host y abrimos http://127.0.0.1:8000/docs desde el navegador.

Ciclo al tocar código

La imagen es una copia del código (COPY . .): un contenedor en marcha no ve los cambios del editor. Hay que reconstruir:

docker rm -f mi-api
docker build -t mi-api:local .
docker run --rm --name mi-api -p 8000:8000 --env-file .env mi-api:local
Nota sobre --rmCon --rm, docker stop borra el contenedor y no hay docker start: hay que volver a hacer run. Para practicar stop → start, lánzalo sin --rm.

Buenas prácticas mínimas

PrácticaMotivo
Imagen slim + requirements.txtReproducible y más ligera
.dockerignore con .env, .git, venvNo filtrar secrets ni hinchar la imagen
Un proceso principal = la APILogs claros; el PaaS reinicia ese proceso
/health ligero y sin authEl hosting puede sondear el servicio
Rebuild tras cambiar códigoLa imagen es una copia; run no ve el editor
Qué no es DockerNo sustituye la seguridad de aplicación (API key, rate limit siguen en el código), no es Kubernetes y no «despliega solo»: el deploy es el siguiente bloque. Multi-stage y HEALTHCHECK existen, pero con python:*-slim + pip basta.

Errores típicos

  • Olvidar -p El contenedor funciona pero el navegador no llega: el puerto no está publicado.
  • Esperar que el contenedor vea el código nuevo Hay que rm -f + build + run.
  • Meter el .env en la imagen Se filtra al compartirla. Va en .dockerignore y entra con --env-file.
  • Usar la forma JSON del CMD No expande ${PORT}; en el PaaS el puerto no coincide.
  • Lanzar docker run con Docker Desktop cerrado Abre Docker Desktop y espera a que el motor esté en marcha.

Deploy de RAG y agentes en cloud

El siguiente paso es que alguien llame a una URL pública HTTPS sin tener Docker instalado. Subimos la imagen a un PaaS (Render): él construye, arranca el contenedor y le inyecta las variables del panel.

Antes (local)
  Cliente → http://127.0.0.1:8000

Ahora (cloud)
  Cliente → https://mi-servicio.onrender.com
                ↓
           contenedor en el PaaS
                ↓
           (si hay historial) Postgres managed
TemaLocalCloud (PaaS)
Cómo arrancadocker run / uvicornBuild desde el repo + start
Secrets.env / --env-fileVariables en el panel
DiscoNuestro SSDEfímero en el web service; BD managed aparte
URLlocalhostHTTPS pública
Cold startCasi noEn planes bajos el servicio puede dormir

La lógica de negocio (agente, tools, API key, rate limit, logs) no se reescribe: viaja en la misma imagen. Render es el PaaS canónico porque encaja con Dockerfile, gestiona secrets por UI y ofrece Postgres managed; Railway, Fly o Cloud Run siguen el mismo patrón: build → servicio web → env → BD managed.

Secrets en el panel

VariableUso

En el código se leen con os.getenv. Si falta un secreto crítico, la app debe fallar claro; nada de defaults de producción hardcodeados. PORT lo inyecta el hosting y el Dockerfile ya usa ${PORT:-8000}.

Health check y logs

/health debe ser ligero (sin LLM) y sin API key: si exigiera clave, el health check del PaaS fallaría. Con historial en Postgres, esperamos:

{"status": "ok", "storage": "postgres"}

Lo que escribimos a stdout (print / logging) aparece en el dashboard de Render (Logs): thread_id, duration_ms y errores sirven igual que en local.

RAG dentro del contenedor

┌─ Contenedor / Web Service ─────────────┐
│  FastAPI                               │
│   · /ask + auth + rate limit           │
│   · grafo / agente + tools             │
│   · tool RAG (misma imagen)            │
│        ↑                               │
│   data/*.txt  (COPY en el Dockerfile)  │
└────────────────────────────────────────┘

Un deploy = un contenedor FastAPI que ya incluye agente + RAG. No montamos un «RAG Service» aparte: con corpus pequeño (guías de demo) añadiría coste y superficie sin aprender nada nuevo de deploy.

EnfoqueCuándo tiene sentido
RAG dentro del API (este sprint)Un producto, un deploy, demos de bootcamp
Microservicio RAG / vector DB cloudEquipos grandes, índices enormes, multi-tenant

Límites: más PDFs = imagen más grande; si cambia el corpus hay que rehacer el deploy (nuevo COPY); un índice enorme en RAM puede tumbar el plan free.

Qué desplegamos

Pieza¿Deploy?
FastAPI (+ agente / tools / RAG)Sí — Render
Postgres managedSí — cuando hay historial
StreamlitLocal, apuntando a la URL cloud (URL base pública + la misma API_KEY)
Redis / vector DB cloudNo (solo mención)

Errores típicos

  • Build OK, pero el servicio cae Falta una variable (API_KEY, GEMINI_API_KEY, DATABASE_URL) o crash al importar.
  • 401 en todo La API_KEY del panel no coincide con el ?api_key= del cliente.
  • Timeout / 504 Revisa ASK_TIMEOUT_SECONDS, el cold start o un LLM lento.
  • CORS en el navegador El origen del front no está en CORS_ORIGINS.
  • Proteger /health con API key El health check del PaaS no puede entrar.

PostgreSQL: local y en la nube

El disco de un contenedor desaparece al borrarlo. Si la API guarda historial, necesita PostgreSQL: en el portátil como contenedor aparte con pgAdmin de visor, y en la nube como servicio managed.

API (uvicorn o contenedor)
        │  DATABASE_URL
        ▼
 PostgreSQL (:5432)
        ▲
   pgAdmin (visor)

Si la API guarda historial (conversaciones, turnos) necesitamos una base de datos real. En este sprint son dos escenarios: Postgres en Docker + pgAdmin en el portátil, y Postgres managed en la nube. Sin DATABASE_URL la app no arranca (no hay fallback a fichero local).

1) Postgres en Docker (local)

docker run --name aire-pg -e POSTGRES_PASSWORD=123456 -d -p 5432:5432 postgres
PiezaSignificado
--name aire-pgNombre del contenedor (puedes usar otro)
POSTGRES_PASSWORD=123456Contraseña del usuario postgres
-p 5432:5432Puerto visible en el PC: localhost:5432
-dEn segundo plano

La BD se llama postgres por defecto. Comprueba con docker ps. La contraseña del contenedor debe coincidir con la de DATABASE_URL.

2) pgAdmin: el visor

Instala pgAdmin 4 → Add New Server → pestaña Connection:

CampoValor
Host name/addresslocalhost
Port5432
Maintenance databasepostgres
Usernamepostgres
Password123456

Tras unos /ask, en esa BD aparecen las tablas del historial (conversation, message). Se crean solas al arrancar la API: no hace falta crearlas a mano.

3) DATABASE_URL: el host cambia según dónde corra la API

postgresql://postgres:123456@HOST:5432/postgres
Dónde corre la APIHOST en la URL
uvicorn en el PC127.0.0.1 (Postgres publicado en el host)
API en Docker (Windows / macOS)host.docker.internal
 
# API con uvicorn en el PC
DATABASE_URL=postgresql://postgres:123456@127.0.0.1:5432/postgres

# API en Docker (Windows/macOS)
DATABASE_URL=postgresql://postgres:123456@host.docker.internal:5432/postgres

Dentro del contenedor de la API, 127.0.0.1 no es tu PC: es el propio contenedor. Por eso cambia el host. Comprobación final: /health debe devolver "storage": "postgres". Si la nube entrega postgres://…, config.py normaliza el prefijo a postgresql:// (el que prefiere SQLAlchemy).

4) Postgres managed en la nube

En un Web Service el disco del contenedor es efímero: el historial no puede vivir «dentro» de la imagen.

FastAPI (Web Service)
        │  DATABASE_URL (Internal)
        ▼
PostgreSQL managed
1
New → PostgreSQL en Render, en la misma región que el Web Service.
2
Copia la Internal Database URL.
3
Pégala como DATABASE_URL en Environment del Web Service y redeploy.
4
Prueba /health → "storage":"postgres" y un /ask con clave.

Para mirar los datos desde tu PC con pgAdmin usa el host externo del panel (y SSL si lo pide el proveedor). La API usa la URL interna.

EntornoPostgresCómo conecta la API
LocalContenedor docker run + pgAdmin127.0.0.1 o host.docker.internal
CloudManagedInternal DATABASE_URL en el panel
Compose, solo menciónDocker Compose define varios servicios en un YAML y es habitual en equipos, pero aquí el camino canónico es más simple: docker run de la API, docker run de Postgres y, en cloud, Web Service + Postgres managed como recursos separados. No desplegamos Compose en el PaaS.

Errores típicos

  • Usar 127.0.0.1 en DATABASE_URL con la API en Docker Apunta al propio contenedor: usa host.docker.internal.
  • Contraseña distinta en el contenedor y en la URL La API no conecta; deben coincidir.
  • Postgres parado docker ps debe mostrar el contenedor; si no, docker start aire-pg.
  • Crear las tablas a mano en pgAdmin Innecesario: la API las crea al arrancar.
  • Esperar el historial en el disco del contenedor Es efímero; el historial vive en Postgres.

Arquitectura y costes

Antes de hablar de automatizar, conviene leer el sistema desplegado con ojos de producción: qué piezas hay, qué límites tiene y qué nos cuesta.

[Cliente: Postman / Streamlit local]
              │ HTTPS
              ▼
     ┌──────────────────┐
     │ PaaS Web Service │  ← FastAPI + agente + RAG (1 contenedor)
     │  API_KEY, rate,  │
     │  logs, timeout   │
     └────────┬─────────┘
              │ DATABASE_URL (si hay historial)
              ▼
     ┌──────────────────┐
     │ Postgres managed │
     └──────────────────┘

     Fuera: Gemini (tokens) · APIs externas

Una sola unidad de deploy para la app. La complejidad «de plataforma» (Kubernetes, service mesh) no entra.

Límites que vas a notar

LímiteEfecto
Cold start (tier free)Primera request tras dormir: varios segundos extra
CPU / RAM del planAgentes + embeddings pueden ir justos; 502 / OOM si te pasas
TimeoutsLos del PaaS + tu ASK_TIMEOUT_SECONDS
Rate limit propioProtege abusos; también limita demos masivas
Cuotas del LLM429 / facturación; independiente del hosting

Dos facturas mentales

🏗️ 1 · Infra

Web Service + Postgres, dominio, etc.

🪙 2 · Tokens / APIs

Cada /ask puede llamar al LLM y a tools externas.

🛟 En demos

Modelos razonables, ASK_TIMEOUT_SECONDS holgado pero finito y siempre API_KEY en el servicio público.

CI/CD con GitHub Actions

¿Cómo evitamos el «a mí me compilaba» en cada push? Con CI: una receta automática que construye y comprueba el servicio. En el sprint nos quedamos en la idea: pip + docker build.

CI · Integración continua

En cada push / PR, una máquina de GitHub clona el repo, instala dependencias y corre checks.

CD · Despliegue continuo

Si el check pasa, desplegar (o dejar un artefacto listo). En el bootcamp lo hace el auto-deploy de Render al hacer push a main.

Sin CICon CI mínimo
«En local pasaba»Misma receta en cada push
Dockerfile roto descubierto en el PaaSdocker build falla antes, en Actions
Regresión en /health o authUn test o script lo pilla

Pipeline mínimo (idea)

# .github/workflows/ci.yml — esquema
name: ci
on:
  push:
    branches: [main]
  pull_request:

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - name: Install
        run: |
          if [ -f requirements.txt ]; then
            pip install -r requirements.txt
          fi

      # Opcional: tests
      # - run: pytest -q

      - name: Docker build
        run: |
          if [ -f Dockerfile ]; then
            docker build -t app:ci .
          fi

Así comprobamos que el servicio al menos construye.

Secretos en Actions

Si algún test necesita claves: GitHub → Settings → Secrets and variables → Actions y en el workflow env: GEMINI_API_KEY: ${{ secrets.GEMINI_API_KEY }}. No imprimas secrets en los logs; para muchos checks basta mockear el LLM y usar una API_KEY de test.

Relación con el PaaS

PatrónCómo
1 · Push a main → auto-deploy del PaaSActions solo valida
2 · Actions hace build y, si pasa, dispara el deployHook / API del PaaS
✅ En el bootcamp basta el patrón 1 + un CI que haga build. Es la idea; sin workout aparte.
❌ No montamos matrices de varias versiones de Python, escaneo de vulnerabilidades enterprise ni preview environments por PR.

Conceptos que debes dominar

  • Imagen vs contenedor; build / run / ps / logs / stop / rm
  • Dockerfile de FastAPI: orden de capas, ${PORT:-8000} y 0.0.0.0
  • .dockerignore y secretos solo en runtime (--env-file / panel)
  • -p host:contenedor; la imagen es una copia: rebuild tras tocar código
  • Render: Web Service + Docker, variables en el panel, /health sin clave
  • RAG dentro del contenedor: un deploy = un servicio
  • Postgres: 127.0.0.1 vs host.docker.internal; Internal vs externa en Render
  • Límites (cold start, RAM, cuotas), dos facturas (infra y tokens) y la idea de CI con docker build
